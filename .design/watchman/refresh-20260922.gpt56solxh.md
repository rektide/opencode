## ConfigDiscovery re-homing

The 2026-09-05 halted composition involved the historical line, whose Config
owner modified the old monolithic `Config.discover`. Upstream commit
`24f6cb51c851` (`fix(core): watch new config files and directories (#46925)`)
replaced that structure with:

- `ConfigDiscovery.discover(options) -> ConfigDiscovery.Sources`;
- `Config.load(sources)` for source materialization;
- `ConfigWatch.plan(sources)` for complete watch-interest derivation; and
- `Config.reconcileWatches`, which retains a `FiberMap` and reconciles the
  complete plan.

The floating compact carrier was created on 2026-09-06 from `cd504dc66ac6`,
which already contains that upstream structure. Therefore this freshen did not
need to transplant the old `Config.discover` hunk or invent new config
plumbing. The existing compact carrier re-homes the behavior at the new seams:

1. Config subscribes to every `ConfigWatch.plan` target with
   `watcher.subscribe(target, requestReload)` and reconciles by source-derived
   key.
2. `feat(core): rerun watcher readiness on native invalidation` makes a
   retained Watchman invalidation rerun that readiness effect before later
   exact updates.
3. `feat(core): retain skill watches across rescans` gives
   `ConfigSkillPlugin` the same retained-interest posture: readiness publishes
   a rescan request, desired keys are collected during each source scan, and
   only obsolete watches are removed afterward.

The locked baseline retains this shape. Its later Config work separates
compatibility roots and adds `Config.update`, but `ConfigWatch.plan`, the
source-derived reconcile loop, and the readiness callback are unchanged. The
location reload family (`b52f24129428`, `b81be469c833`, `7390832f135a`) changes
location/client/TUI lifecycle behavior rather than watcher-interest ownership.
No policy choice or new configuration design was required.
