# model-ident — render persisted per-message model attribution

## Motivation

The session schema already persists the exact `Model.Ref` that generated
**every assistant message** (`Session.Message.Assistant.model`,
`packages/schema/src/session-message.ts:210`) — including thinking
variants, `-m` overrides, and sessions predating any plugin. Nothing ever
renders it to the LLM: `to-llm-message.ts` reads `message.model` only to
decide provider-metadata reuse, and the model-facing view carries no
attribution. The result: a session that switched models mid-conversation
has no model-visible record of which model produced which stretch.

This patch renders the persisted attribution where it changes, so the
conversation itself records which model generated each section.

## Patch shape

- `packages/core/src/session/runner/to-llm-message.ts` — `toLLMMessages`
  gains an `AttributionOptions` parameter. With `attribution: true`, the
  first assistant message of each model stretch (the first assistant
  message, and the first after any provider/model/variant change) is
  prefixed with a text part:

  ```
  [generated by: zai-coding-plan/glm-5.3#max]
  ```

  Boundary-only rendering keeps the added tokens to one short line per
  stretch. Attribution advances only when a marker actually lands, so an
  empty first turn of a stretch defers the marker to the next assistant
  message.
- `packages/core/src/session/model-request.ts` and
  `packages/core/src/session/generate-node.ts` — both `toLLMMessages` call
  sites read the setting and pass it through.

## Setting

`OPENCODE_MODEL_ATTRIBUTION` — env-backed boolean, **default false**
(historical behavior preserved, per the working-stack upstreamability
precedent; same pattern as `OPENCODE_PROMPT_CACHE_DIAGNOSTICS` in
`model-request.ts`, and deployed the same way as
`OPENCODE_LOCATION_CACHE_TTL` in `~/.zshenv`). Enable with
`OPENCODE_MODEL_ATTRIBUTION=1`.

## Properties

- No new turns, no inbox input, no plugin state: pure rendering of
  persisted fields at compile time. Restart-proof and reload-stable by
  construction — the rendered sequence is a pure function of stored data.
- Retroactive: covers old sessions and `-m` request-time overrides,
  because the data was always persisted per message.
- Cache: enabling changes assistant-message content mid-history, costing a
  one-time re-cache of each session's suffix; stable afterwards (stored
  refs never change).

## Relationship to the plugin

`~/src/opencode-model-id` is the **less-capable plugin-only predecessor**,
kept working on unpatched hosts: it appends durable synthetic records
(`[model: …]`, `[model-switched …]`, steer-delivered) derived from
request-time refs. Compared to this patch it cannot attribute turns
retroactively (records exist only from plugin install onward), costs an
acknowledgment turn per record, and rebuilds its tracking from history on
cold start. With this patch enabled, the plugin's records are redundant
for attribution; its `model_identity` tool remains independently useful.

## Verification

- `packages/core`: focused `test/session-runner-message.test.ts` — 25 pass
  (21 pre-existing + 4 new: default-off renders nothing; boundary markers
  only at stretch starts; variant-less refs; empty-turn deferral).
- `bun run typecheck` (tsgo) clean from `packages/core`.

## Upstreamability

Default off; additive options parameter; renders data the host already
persists. Natural upstream shape. If adopted upstream, the local patch
evaporates on refresh (adopt-upstream precedent from the
subagent-continuation decision).

# Addendum — startup status announcement (2026-08-30)

## The gap

Stretch markers are retrospective: they can only land on persisted assistant
messages. Three situations therefore told the model nothing about itself:

- a session's **first request** (no assistant messages exist yet);
- any request made **after a model change but before the new model has
  responded** (`/model` switch, `-m` override, agent switch to another model);
- the **first request after compaction** (history collapses to a summary with
  no attributable assistant messages).

The model would generate its first response under the new identity before any
record of that identity existed in the conversation.

## The fix

When attribution is enabled and the folded history leaves the **request's**
model unattributed (no attributed stretch at all, or the last attributed
stretch differs in provider, id, or variant), `toLLMMessages` appends one
final user-role message:

```
[generating with: zai/glm-5.3#max]
```

The note is prospective — it describes the request being built, not stored
data — so it is **not persisted** and never becomes session state. It
self-extinguishes: once the model's first response persists, that response
carries its own `[generated by: …]` marker and the request model counts as
attributed, so the announcement disappears from every later request. The
empty-turn deferral rule composes correctly: a stretch with no assistant
content stays unattributed, keeping the announcement in place.

## Properties

- **Cache**: the note is appended at the tail, leaving every earlier message
  byte-identical, so the prompt-cache prefix is unaffected; it vanishes on the
  following request exactly where the new assistant message lands anyway.
- **Placement**: end of compiled history. In `model-request.ts` it precedes
  the step-limit `MAX_STEPS_PROMPT` nudge; in `generate-node.ts` it precedes
  the instruction update and the live prompt. Both read as a status line
  before the active turn.
- **No new setting**: rides the existing `attribution` flag. Per the
  implement-without-options-first decision (2026-08-30), a real preferences
  surface — config-file-backed toggle rather than env-only, potentially
  splitting retrospective markers from the prospective announcement — is a
  deferred follow-up, not part of this patch.
