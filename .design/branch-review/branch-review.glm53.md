## Session core group

### instance-seam
**Status:** PR #45413 (OPEN) · base v2 · Kit Langton · 6 commits · last activity 2026-08-26
**What it does:** Introduces a values-constructed session environment for embedders: `SessionEngine.make({ directory, model, tools, agents, catalog })` compiles the "engine tier" of the location graph (`sessionEngineGroup` = runner entry, prompt-admission services, Tool/Agent/Catalog registries) with discovery, plugins, MCP, and snapshots replaced by no-op layers, then populates registries through the same draft APIs plugins use. Sessions bind to the environment via a new process-local `SessionEngineBindings` map (`bind`/`get` by Session ID), and `SessionExecution.drain` resolves `bindings.get(sessionID)` before falling back to `LocationServiceMap.get(session.location)`, pinning one environment per busy period. MemoMap capture + `compileWithHoistedGlobals` ensure each environment dedupes against the running Database/Bus/SessionStore instead of building duplicates.
**Where:** `packages/core/src/session-engine.ts` (new, 145 lines), `packages/core/src/session/engine-bindings.ts` (new), `packages/core/src/session/execution.ts`, `packages/core/src/location-services.ts` (engine-tier extraction + compile-time subset guard), `packages/core/test/session-engine.test.ts` (new).
**Review:** This is the lean successor to the closed session-capabilities approach (+404/−27 vs +2511/−370) — same embedding goal, but binding a whole service graph per session instead of pinning individual capability values per busy period. Quality is high: the new test boots a real application root and proves a durable drain through the real `SessionExecution` path with global dedupe and reconnection-by-ID, and the compile-time `SessionEngine ⊆ LocationServices` guard is a nice structural safety. It deliberately deviates from the "SessionExecution discovers placement through `SessionStore` plus `LocationServiceMap.get`" invariant by inserting a Session-ID-keyed binding layer — self-aware and documented, but the AGENTS.md invariant text will need updating if merged. Honest scope notes (attachment/skill/fork paths still resolve `locations.get`; no changeset — it's explicitly a discussion draft), so not merge-ready as-is.

### assign-seam
**Status:** PR #45813 (OPEN) · base v2 · Kit Langton · 4 commits · last activity 2026-08-28
**What it does:** Replaces `LocationServiceMap` with `InstanceMap`, separating *assignment* (which requests share an instance, `forSession(session)`) from *construction* (explicit-location `get(ref)`). `Instance.Key` is a Core-local nominal string derived deterministically from a canonical location (normalized directory, Windows separators, workspace identity); an `Entry` retains the canonical ref as construction input while hashing/equaling only on the key, all on the single existing Effect `LayerMap`/`RcMap`. Bus routing, debug inventory/eviction, server middleware, and ~20 session call sites move to key-based or `forSession` lookup.
**Where:** `packages/core/src/instance-map.ts`, `instance-map/internal.ts`, `instance-key.ts`, `location.ts` (`canonical`/`instanceKey`), `session.ts`, `bus.ts`, `location-activity.ts`, `packages/server/src/middleware/*` and `handlers/debug.ts`; new `test/instance-map.test.ts` (216 lines), `location-stub.test.ts`, `server/test/debug.test.ts`; updates `AGENTS.md` and `specs/v2/{session,catalog-config-plugin-lifecycle}.md`.
**Review:** A behavior-preserving seam introduction — the default policy derives keys from the canonical location, so the main server keeps one-instance-per-location while opening the boundary that instance-seam-style bindings (or future placement semantics) need; the PR's own table scopes custom assignment policy as follow-up. It's the broadest mechanical rename of the group (49 files, +831/−411), but the diff is disciplined and verification is unusually thorough (full Core 3794 pass, 33 typecheck tasks, real HttpApi debug test). Fits the "SessionRunner Location-scoped / explicit workspace identity reserved" invariants since Location.Ref remains the construction input. Main concern is merge-order coupling: it collides textually with instance-seam's `execution.ts` changes and should land before/with them to avoid churn.

### step-machine
**Status:** PR #46021 (CLOSED unmerged) · base v2 · Kit Langton · 2 commits · last activity 2026-08-28
**What it does:** Replaces the logical-step retry loop and physical-attempt loop in the runner with one explicit state chart (`PreparingAttempt → ObservingProvider → FinalizingProvider → AwaitingTools → RecoveringOverflow → SettlingAttempt → BackingOff → Done`, plus a `Stopping` cancellation path), driven by a new generic 236-line runtime (`src/effect/state-machine.ts`). States/operations/events are `Data.TaggedEnum` values dispatched via exhaustive `$match` tables, with effects confined to an interpreter; `stopAndJoin` aggregates cancelled generations' exits; each provider-event publication is uninterruptible so in-memory marks can't outrun the durable commit.
**Where:** `packages/core/src/session/runner/step-machine.ts` (new, 402 lines), `packages/core/src/effect/state-machine.ts` (new), rewrites of `runner/llm.ts` and `runner/step.ts`; 527-line `test/session-step-machine.test.ts`, 415-line `test/effect/state-machine.test.ts`.
**Review:** No PR comments and no supersession found — v2 still runs the `while (true)` loops in `runner/llm.ts`, and `step-machine.ts` does not exist on v2; it reads as a design-review draft that was closed without adoption (opened and closed the same day). The work itself is serious: it preserves the one-`llm.stream`-per-Physical-Attempt and cancellation-settles-before-propagation invariants, and the verification section is candid (one unrelated full-suite flake disclosed). The cost is real, though — +425 net session-production lines on the hottest correctness path plus a new generic runtime to maintain — and the PR itself frames it as "an explicitness and ownership tradeoff, not a claim of fewer lines." If the orchestration rules in the chart (uninterruptible publication, stop-and-join semantics) get re-landed, they're worth salvaging as documented policy regardless of the state-machine machinery.

### session-capabilities
**Status:** PR #45481 (CLOSED unmerged) · base v2 · Kit Langton · 12 commits · last activity 2026-08-27
**What it does:** Adds an Effect-native `Session.Service.open` that creates or adopts a durable session with in-process *live* capabilities: `Source`-valued model (required), tools, instructions, permissions, limits, and a retirement hook. **Where:** `packages/core/src/session/resolve.ts` (new, 291 lines — ownership index, busy-period resolution), `session/capabilities.ts` (new), `source.ts` (new), `permissions.ts`, `session.ts`, `session/context.ts`, `kv.ts`, a 385-line `tool.ts` rework for value tool snapshots, `packages/schema/src/tool.ts`; 871-line `session-capabilities.test.ts` plus a 223-line recovery test.
**Review:** Closed without comment the day after instance-seam opened — the two solve the same embedding problem, and instance-seam's whole-graph binding (+404) clearly won over this per-capability pinning design (+2511). Salvage evidence: exactly 2 of its 12 commits were cherry-picked into v2 by patch-id — `6b27cec5ac` "exclude Redis from workerd socket bundles" → v2 `8a3e9890d2`, and `7ee5bde599` "make websocket overflow fixture deterministic" → v2 `2142de87dd` — i.e. the incidental fixes landed, the capability machinery did not. ### inbox-reorder

### state-pull
**Status:** PR #45822 (OPEN, marked draft) · base v2 · Kit Langton · 4 commits · last activity 2026-08-28
**What it does:** Reworks the `State` registry primitive so reads *pull* pending definitions synchronously: accepted transform/dispose/reload operations mark the snapshot dirty and `get()` rebuilds it from `initial` + ordered transforms + a new synchronous `prepare` hook, then caches. The old `finalize` hook is split into `prepare` (derived data, read path) and `notify` (observation only, batched per batch-completion, debounced per reload), batches coalesce notifications rather than visibility, reload callers in one debounce window share one `Deferred`, and observer failures never hide committed changes.
