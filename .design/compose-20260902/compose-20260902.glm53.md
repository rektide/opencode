# Compose friction 2026-09-02

Standing record of the three frictions the `working-20260902` rebuild
surfaced. Per the new report requirement in
[`patches-apply.md`](../../../../../ado/patches-apply.md), each rebuild
session closes with one of these; this is the first.

## 1. cache-ttl: deployment env leaks into eviction tests — FIXED

**Problem.** `LocationActivity.node` builds with `layer()` whose
time-to-live falls back to `OPENCODE_LOCATION_CACHE_TTL` when no explicit
option is given (the feature's whole point). The location-layer tests
exercise eviction against the 60-minute default — but the layer resolves
the env var *at build time*, so any shell carrying the live service's
`"8 hours"` export makes the two lifetime tests fail. Documented on
2026-09-01, rediscovered by instrumentation on 2026-09-02 (the
embarrassing detour), now fixed.

**Fix (landed as compose rider `174bd670`)**: the test graph replaces
`LocationActivity.node` with a pinned node — same service tag, same deps,
`layer({ timeToLive: "60 minutes" })` — so the suite is hermetic
regardless of ambient env. Verified with the live export set: 13/13.

**Eases still open.**
- Port the same pin into the cache-ttl feature workspace
  (`~/src/opencode-cache-time`) so the fix survives the next freshen
  instead of living only in the composition.
- Consider having `resolveTimeToLive` log the resolved source
  (option/env/default) once at layer build — a one-line breadcrumb that
  would have made the 2026-09-02 detour a five-second grep.
- Upstream candidate: tests that read env-sensitive defaults through
  node layers are the general pattern here; if more appear, a
  `test/env.ts` helper that snapshots and scrubs `OPENCODE_*` vars per
  suite is the systemic fix.

## 2. AGENTS.md is both repo content and live agent instructions

**Problem.** Two entangled behaviors bit this compose:

1. *Lineage noise:* the watchman line's `cleanup docs` commit deletes its
   workspace-local `AGENTS.md`. That is workspace hygiene, not feature
   content — but at compose time it surfaces as a delete/modify conflict
   against upstream's actively-maintained repo `AGENTS.md` (it changed
   branch guidance mid-session).
2. *Context pollution:* during resolution, the working copy's
   `AGENTS.md` contains live conflict markers — and the agent harness
   reads it as instructions. This session twice received system
   instructions partially built from conflict-marker text. Harmless here
   (the markers were recognizable and ignored) but it is untrusted-text
   injection into the instruction channel.

**Eases we could do.**
- **Compose procedure**: resolve `AGENTS.md` (and any `*.md` instruction
  file) *first*, taking upstream's side on hygiene deletions, before any
  other work in the workspace. One line in the patches-apply checklist —
  added this session.
- **Workspaces**: stop tracking workspace-local `AGENTS.md` in feature
  lines at all (gitignore it per-workspace); if guidance is needed, it
  belongs in `.design/` docs that compose deliberately.
- **Harness (upstream idea)**: an agent runner could refuse/skip
  `AGENTS.md` files containing conflict markers rather than parsing them
  as instructions. Small, cheap defense; worth an upstream issue.

## 3. Upstream jj-vcs movement — standing watch

**Problem.** The ours-not-theirs decision is conditional ("ours remains
the substrate **until** `jj-vcs-plugin` merges"), but nobody was
re-checking the condition, and the cost of upstream movement under an
unfreshened feature goes unseen until compose.

**What actually made the jj-vcs compose hard — three separate facts,
keep them distinct.**

1. **Two upstream refactors landed and stayed**, both during jj-vcs's
   3-week base window (between its base `c29968bf0850` and our 09-01
   base `43d09b9d75ad` — verified present at `43d09b9d`, *not* in the
   09-01→09-02 delta):
   - the **VCS-plugin provider API** (`0ab2d783e8`/`b71291c05a`,
     #44992/#44993): git/hg became internal plugins registering
     `VcsDefinition`s; core `vcs.ts` is now only a registry;
   - the **project-copy → worktree rename**: `project/copy.ts` →
     `worktree.ts`, `schema/project-copy.ts` → `schema/worktree.ts`,
     `project.directories` → `worktree.*` endpoints, `project_directory`
     table → `worktree`.
   Our line targeted both old seams. Porting onto the new ones was the
   entire compose cost, and it was **unavoidable regardless of any
   upstream check** — the refactors are real and staying.
2. **The 2026-09-01 freshen could not have warned us**: none of the six
   features accepted then touch `vcs.ts` or the copy subsystem, so the
   reshaped seams surfaced only when jj-vcs (composed unfreshened, by
   operator choice) entered the stack. A freshen of jj-vcs itself before
   composing would have moved this cost into the freshen step — same
   work, better litigated place.
3. **The markers drop did not affect our difficulty at all.** Upstream's
   declarative-markers machinery (`4eaf533cd03c` #45192) merged into v2
   2026-08-26 and was removed 2026-08-31 (`5d73a5789f`). Our line never
   built on it — we borrowed fs-only detection/pointer-file *ideas* only.
   What the drop orphaned is **upstream's own `jj-vcs-plugin` branch**
   (it refactors jj onto machinery v2 no longer carries), which is why
   the "swap detection for theirs at merge" clause currently has nothing
   to swap to. If a doc sentence ever implies the drop caused our port
   pain, it is wrong.

**State as of this doc.** The background agent's check landed: **nothing
of upstream's jj line moved** — `bee852b5`/`46465000` still unmerged,
`jj-vcs-plugin` unmoved since 2026-08-26 and orphaned as above. v2
carries no jj code at all; ours is the only live jj line. Full findings
and SHAs:
[`design/jj-vcs/upstream-check-20260902.glm53.md`](file:///home/rektide/src/opencode-jj-vcs/design/jj-vcs/upstream-check-20260902.glm53.md)
in the jj-vcs workspace; v2 has since advanced to `33dd4e3ba8e9` with
zero jj/vcs/worktree content, so the next freshen rides it cleanly.

**Eases we could do.**
- Make the upstream check a **fixed pre-flight step of every rebuild**:
  `git fetch` + the five rev-parse/merge-base probes, recorded in the
  refresh notes. It would not have avoided this port (fact 1) but kills
  dead plan-branches early (fact 3: "port their detection commits" was
  unlandable-in-principle and we held it open all day).
- When a tracked upstream line moves, note *which of our seams it
  threatens* in the same check — the worktree rename was visible in any
  `git log --diff-filter=R` scan of the base window.
- Freshen a long-stale feature *before* promoting it into a rebuild, even
  when the operator waves the wave for the standing features — the stale
  line is where compose cost concentrates.
